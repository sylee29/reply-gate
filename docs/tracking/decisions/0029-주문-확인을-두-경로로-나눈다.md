# 0029 — 주문 확인을 두 경로로 나눈다

날짜: 2026-10-12. 상태: 채택.

주문번호만으로 개인정보가 포함된 주문 근거를 읽는 경계를 닫는다. 계정 인증을 도입하는
대신 단일 개발자·합성 데이터 데모 범위에서 두 확인 경로와 주문별 실패 제한을 편입한다.

1. 전화번호 뒤 ASCII 네 자리를 입력하면 서버가 주문의 전화번호에서 숫자를 추린 마지막
   네 자리와 비교한다. 일치하고 잠금이 아니면 기존 근거·답변 흐름을 계속한다.
2. 생략하면 존재하는 주문의 **상품명만** 확인 질문으로 보이고 `awaiting_confirmation`으로
   저장한다. 원문을 보관하며 옵션·수량은 질문에 넣지 않는다. 상품이 맞다고 확인하면
   같은 문의 ID로 개인정보 없는 처리를 진행하고, 아니라고 하면 `order_unconfirmed`로 인계한다.

두 번째 경로는 주문 존재와 상품명을 노출한다. 이 정보 노출은 수용한 대가다. 네 자리는
강한 본인 인증이 아니며 가능한 값이 10,000개다. 같은 주문번호 문자열에서 연속 5회 실패하면
15분 잠그고, 성공 또는 잠금 만료 뒤에는 0부터 센다. 없는 주문도 같은 제한을 받는다.
실패·없는 주문·잠금은 같은 응답이다. 상품 확인은 이 횟수와 잠금에 영향을 받지 않는다.
악의적인 실패로 정상 주문자를 잠글 수 있다. IP별·전역 레이트리밋은 도입하지 않는다.

입력한 뒷자리는 비교 중 메모리에만 있고 기록에는 서버 비밀 `PHONE_HMAC_SECRET`을 쓰는
HMAC-SHA256만 남긴다. 비밀은 `SecretStr`·표시 억제 필드이며 문의 처리 시에만 필수다.
단순 해시는 10,000개를 전수 대입해 복원할 수 있다. HMAC도 키가 유출되면 이 한계가 되살아난다.
실패 제한 표는 주문번호·횟수·시각만 저장하며 앱 계정만 접근한다.

상품 확인 경로는 SQL 허용목록에서 고객 이름·전화·이메일·배송지 열을 제외한다. AST가
별칭·CTE·계산식 안쪽 참조도 검사하고, `*`는 명시 열을 요구하며 거부한다. 이름·주소는
정규식 탐지가 아니라 원천 근거 제외로 보호한다. L1에는 빈 PII 허용목록을 넘겨 패턴형
개인정보 답변을 기각한다. 초안/L2에는 허용된 근거를 유지한다.

확인은 생성 시각부터 기본 30분(설정 가능)이며, 대기이고 선점 시각이 없는 행만 원자적으로
선점한다. 선점은 별도 짧은 트랜잭션으로 먼저 확정하고, 결과·시도·근거 저장은 함께 롤백된다.
외부/DB 오류 뒤에도 대기+선점 시각이 남아 다음 확인은 409다. 다시 진행하려면 새 문의를 만든다.
전화 실패/성공0도 별도 짧은 트랜잭션이므로 모델 오류에 되돌아가지 않는다.
호출자가 넘긴 앱 연결의 기존 변경은 임의 커밋하지 않는다.
동시 확인의 하나만 처리하고 나머지는 409다. 만료 상태는 대기로 남는다.

기록 GET에 인증을 추가하지 않는다. UUID4 URL을 아는 사람은 기록을 볼 수 있는 **능력 URL**
성격이므로 링크 공유가 접근 권한 공유다. 사용자 계정 인증·일반 인가·멀티테넌시·배포는 범위 밖이다.

기존 볼륨은 삭제하지 않는다. 추가 열·표는 `IF NOT EXISTS`, 상태·사유·종결 모양과
L1 NULL 쌍 제약은 `DROP CONSTRAINT IF EXISTS` 뒤 추가하는 멱등 SQL로 적용한다.
골든셋은 바꾸지 않고 평가 도구가 주문 픽스처의 뒷자리를 채워 정당한 주문자로 실행한다.
